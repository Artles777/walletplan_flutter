# Текущий функционал

Этот документ фиксирует текущее состояние приложения.
Его задача: быстро показать, что уже есть в продукте, что является заглушкой,
и что нужно обновлять при добавлении новых фич.

## 1. Назначение приложения

Приложение называется `walletplan`.
Репозиторий проекта: `walletplan_flutter`.

`walletplan` это Flutter-приложение для учёта личных финансов.
Сейчас проект находится на ранней стадии: основная навигация уже собрана,
часть UI существует как рабочий каркас, а большая часть доменной логики пока
представлена локальными заглушками.

## 2. Текущая архитектура

### Технологический стек
- Flutter + Material 3
- `beamer` для роутинга
- `flutter_compositions` для локального состояния и composable-хуков
- `slang` / `slang_flutter` для локализации
- `intl` для форматирования валют
- `build_runner` для кодогенерации

### Основные точки входа
- `lib/main.dart`
- `lib/router/root_delegate.dart`
- `lib/router/base_delegate.dart`
- `lib/pages/main/main.page.dart`

### Навигационная схема
- Корневой маршрут приложения по умолчанию: `/app/transactions`
- Корневой `rootDelegate` отвечает за:
  - `/signIn`
  - `/addIncomeOrExpense`
  - `/app/*`
- Вложенный `baseDelegate` отвечает за нижние вкладки:
  - `/app/transactions`
  - `/app/accounts`
  - `/app/plans`
  - `/app/analytic`

## 3. Реализованные пользовательские сценарии

### 3.1 Главный shell приложения

После запуска пользователь попадает в основной shell:
- верхний `AppBar`
- боковое меню `Drawer`
- контент активной вкладки
- центральная floating action button
- нижняя navigation bar на 4 раздела

#### Что показывает `AppBar`
- Текущий баланс пользователя
- Текущий активный счёт пользователя
- Иконки действий поиска и настроек

Важно:
- по продуктовой логике баланс и счёт являются динамическими данными и должны
  зависеть от данных пользователя
- в текущей реализации эти значения пока захардкожены как UI-заглушка
- обработчики действий пока пустые

### 3.2 Нижняя навигация

Доступны 4 вкладки:
- `Транзакции`
- `Счета`
- `Планы`
- `Аналитика`

Что работает сейчас:
- активная вкладка синхронизирована с URI
- нажатие на пункт навигации переключает вложенный маршрут через `baseDelegate`
- для неверного индекса маршрута используется безопасный fallback на
  `/app/transactions`

### 3.3 Вкладка "Транзакции"

Это единственная вкладка, где уже есть рабочая локальная логика данных.

Что происходит сейчас:
- при монтировании запускается загрузка через `useTransactions()`
- отображается `LinearProgressIndicator` во время загрузки
- после загрузки показывается список транзакций
- при ошибке показывается текст ошибки

Текущее состояние данных:
- данные локальные, не из backend
- `useTransactions()` возвращает одну тестовую транзакцию
- структура транзакции уже выделена в отдельную модель:
  - `id`
  - `dateTime`
  - `title`
  - `subtitle`
  - `accountLabel`
  - `amount`
  - `currencySymbol`
  - `icon`

Поддерживаемая логика в `useTransactions()`:
- refresh-загрузка
- пагинация через `offset` / `limit`
- локальный `upsert`
- локальное удаление
- обработка ошибки
- контроль `loading`

Ограничения текущей реализации:
- нет реального datasource
- нет repository / API слоя
- в UI пока отображается только `title` транзакции
- нет карточек, группировки по датам, сумм и пустого состояния

### 3.4 Вкладки "Счета", "Планы", "Аналитика"

Эти разделы уже подключены в роутинг и нижнюю навигацию, но пока являются
заглушками через `Placeholder`.

Это означает:
- переход по вкладкам работает
- доменная логика для этих разделов ещё не реализована

### 3.5 Flow добавления дохода / расхода

В приложении уже есть отдельный сценарий открытия экрана добавления операции.

#### Как он открывается
- tap по FAB открывает расход:
  `/addIncomeOrExpense?type=expense`
- drag FAB вверх открывает доход:
  `/addIncomeOrExpense?type=income`

#### Что уже реализовано
- распознавание типа операции через query-параметр `type`
- переключение между вкладками `Расход` / `Доход`
- синхронизация выбранной вкладки с URI
- возврат назад через root beamer
- отдельная composable-логика для FAB:
  - прогресс анимации
  - порог срабатывания
  - обработка tap
  - обработка vertical drag
  - защита от повторного запуска во время lock-state

#### Что пока не реализовано
- реальные формы добавления
- валидация
- submit
- сохранение данных

Сейчас:
- `AddExpenseFormWidget` это `Placeholder`
- `AddIncomeFormWidget` это `Placeholder`

### 3.6 Экран входа

Маршрут `/signIn` уже объявлен в корневом роутинге, но сам экран пока
реализован как `Placeholder`.

### 3.7 Локализация

Поддерживаются две локали:
- `ru`

Сгенерированные файлы:

## 5. Известные ограничения текущей версии

- Нет реального backend или локального persistence-слоя.
- Нет полноценной доменной модели счетов, планов и аналитики.
- Нет авторизации.
- Нет рабочих форм создания дохода и расхода.
- Нет edit/delete flow для операций через UI.
- App bar, drawer и часть страниц пока используют тестовые данные и заглушки.

## 6. Как обновлять этот документ при новых фичах

При добавлении нового функционала нужно обновлять:

1. Этот файл.
2. `README.md`, если меняется точка входа в проект или запуск.
3. Соответствующие тесты.

Минимум, который нужно дописывать в документацию для каждой новой фичи:
- пользовательский сценарий
- входной маршрут или место входа в UI
- текущее состояние данных
- ограничения и что ещё не реализовано
- ссылка на тесты, которые страхуют поведение
